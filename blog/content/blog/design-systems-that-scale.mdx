A design system is useful when it removes repeated decisions while preserving the decisions that matter. The goal is not a catalogue of every possible component. It is a shared language.

## Start with relationships

Before naming tokens, map the relationships that repeat across the product: foreground against background, compact against spacious, quiet against emphatic.

### A practical token stack

1. Primitive values describe the raw palette and scale.
2. Semantic tokens explain intent, such as `text-muted` or `surface-raised`.
3. Component tokens exist only where a component has a stable, specific need.

```css
:root {
  --space-unit: 0.25rem;
  --surface-raised: oklch(1 0 0);
  --text-muted: oklch(0.48 0 0);
}
```

## Document the exception

When a product team breaks a rule, the exception should explain what new requirement appeared. That record is often more valuable than another component variant.
